# Database Design

## Conventions

- **Primary keys:** `UUID` (v4), generated by Python (`uuid4`) — avoids leaking row counts and works across distributed inserts.
- **Timestamps:** every table has `created_at` / `updated_at` (`TIMESTAMPTZ`, server default `now()`; `updated_at` maintained by the app or a DB trigger).
- **Naming:** snake_case tables (plural) and columns. Alembic enforces consistent constraint naming via `naming_convention`.
- **Enums:** native PostgreSQL enums for fixed vocabularies.
- **Soft delete:** only where business value exists (`projects.archived_at`). Users/tasks are hard-deleted in V1; revisit later.

     │               │   TASKS   │◄────────│ PROJECT_MEMBERS │
     │               └─────┬─────┘         └─────────────────┘

\* `users ↔ organizations` is **many-to-many through `memberships`** — a user can belong to multiple orgs with different roles.

### memberships

The pivot between users and organizations. **This table is the heart of RBAC and multi-tenancy.**

| Column | Type | Constraints |
|---|---|---|
| id | UUID | PK |
| organization_id | UUID | FK → organizations.id, ON DELETE CASCADE, NOT NULL |
| user_id | UUID | FK → users.id, ON DELETE CASCADE, NOT NULL |
| role | org_role enum | NOT NULL, default MEMBER |
| created_at / updated_at | TIMESTAMPTZ | NOT NULL |

Constraints: `UNIQUE (organization_id, user_id)`.

Enum `org_role`: `OWNER`, `ADMIN`, `MANAGER`, `MEMBER`.

Rule enforced in service layer: an org always keeps ≥1 OWNER (last owner cannot be demoted/removed).

### project_members

Controls *visibility* inside an org (a MEMBER doesn't see all projects).

| Column | Type | Constraints |
|---|---|---|
| id | UUID | PK |
| project_id | UUID | FK → projects.id, ON DELETE CASCADE, NOT NULL |
| user_id | UUID | FK → users.id, ON DELETE CASCADE, NOT NULL |
| created_at | TIMESTAMPTZ | NOT NULL |

Constraints: `UNIQUE (project_id, user_id)`.

Visibility rules:
- OWNER/ADMIN/MANAGER of the org: see all org projects.
- MEMBER: sees only projects where a `project_members` row exists (or tasks are assigned to them).

### activities (audit trail)

Append-only. Never updated, never deleted by the application.

| Column | Type | Notes |
|---|---|---|
| id | UUID | PK |
| organization_id | UUID | FK → organizations.id, NOT NULL — tenancy anchor |
| project_id | UUID | FK → projects.id, NULL |
| task_id | UUID | FK → tasks.id, NULL |
| actor_id | UUID | FK → users.id, NOT NULL — who did it |
| action | VARCHAR(100) | e.g. `task.status_changed`, `member.role_updated` |
| entity_type | VARCHAR(50) | `task`, `project`, `membership`, ... |
| entity_id | UUID | Which entity was acted upon |
| old_value | JSONB | Snapshot before (e.g. `{"status": "TODO"}`) |
| new_value | JSONB | Snapshot after (`{"status": "IN_PROGRESS"}`) |
| created_at | TIMESTAMPTZ | NOT NULL |

Indexes: `(organization_id, created_at DESC)`, `(task_id, created_at DESC)`.

Written synchronously in V2 (same transaction as the change — guarantees audit accuracy); moved to background jobs in V3 only for non-critical notification side-effects.

## Migration Strategy (Alembic)

- One migration per schema change; migrations are code-reviewed like everything else.
- Migrations must be **reversible** (`downgrade()` implemented).
- Auto-generate with `alembic revision --autogenerate -m "..."`, then **manually review** — autogenerate misses enum changes and renames.
- Enum values are additive-only in place (adding a value is safe; renaming/removing needs a new enum + swap migration).
- Local dev: `alembic upgrade head`. CI: run migrations against a disposable DB to prove they apply cleanly.

## Data Integrity Rules Summary

1. Every tenanted row carries its own `organization_id` (or reaches it via one join) — this is what makes scoped queries cheap and reliable.
2. Cascading deletes flow downward: org → memberships/projects → tasks → comments/activities.
3. Cross-org references are impossible at the service layer: you can only assign a task to a user who is a member of that task's org (validated in service, not just DB).
